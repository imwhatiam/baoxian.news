# 两个调研：Angular 页面怎么抓、产品类信源有哪些

日期：2026-10-23。这是工作笔记，不是站点配置。

## 一、Angular 渲染的页面怎么拿内容

### 先说结论

能不用浏览器就别用。这个站的采集器是 Node 单进程，塞一个常驻 Chromium 进去，镜像多 400MB、内存多 300–500MB，只为了监管总局每天十来条，不划算。真要做，单独起一个渲染服务，别动主站。

### 开源工具对比

| 工具 | 形态 | 体积/内存 | 维护状态 | 判断 |
|---|---|---|---|---|
| Playwright | Node/Python 库，自带 Chromium | 只装 chromium-headless-shell 约 400MB，渲染时 300MB+ | 活跃，微软维护 | 首选。自动等待、并发上下文省内存 |
| Puppeteer | Node 库，Chrome for Testing | 约 400MB，比 Playwright 略轻 | 活跃，Chrome 团队 | 简单抓取够用；反爬有 puppeteer-extra-stealth |
| browserless | 把 Chrome 包成 HTTP 服务 | 同 Chromium | 活跃，开源版有并发限制 | 多语言共用时省事，单项目没必要 |
| Splash | 轻量渲染服务（QtWebKit），Lua 脚本 | 小 | 3.5 版停在 2020，引擎老；scrapy-splash 在 Scrapy 2.16+ 直接导入失败 | 不要用 |
| Rendertron | Google 的预渲染服务 | 小 | 官方已归档，依赖有未修漏洞 | 不要用 |
| Jina Reader | 托管服务，`r.jina.ai/` 前缀 | 零运维 | 活跃 | 本机实测连不通（连接被重置），而且要 key，放弃 |

### 本项目的三种接法

1. **直接找它的接口**（最省）。Angular 页面背后一定有 JSON 接口，`nfra` 现在用的就是这种。问题是接口会变：今天实测 `nfra` 的 `SelectDocByItemIdAndChild` 已经返回 404，三个监管总局信源下次检查就会失败。所以要有人盯着。
2. **托管渲染**（Jina 这类）。零运维，但本机网络不通，且按次计费。
3. **自建渲染服务**（推荐，如果确实要正文）。一个 `mcr.microsoft.com/playwright` 或 node + `chromium-headless-shell` 的容器，只暴露 `POST /render {url, waitFor}`，返回渲染后的 HTML；再写个几十行的小脚本，把渲染结果解析成条目，走 `/api/ingest/items` 推进来，信源类型记 `external`。好处是浏览器挂了不影响主站，也不需要改框架的采集器。

### 建议

为 `nfra` 的正文上一套浏览器不值。当下更该做的是：把 404 的接口找回来（打开监管总局页面看 Network，找新的 JSON 路径）。只有当你还要抓别的 JS 站（比如中保协产品库）时，再上第 3 种方案。

## 二、产品类信源

### 官方产品库基本不能自动采

| 来源 | 内容 | 能不能采 |
|---|---|---|
| 中保协「人身保险产品信息库」 | 2009 年以来 4 万多款产品、15 个维度（条款、费率表、现金价值表、说明书） | 不能。旧的 `product.php` 现在 302 回首页，新版是 JS 应用，只能人工查 |
| 金融产品查询平台 jrcpcx.cn | 监管指导的统一查询入口，含保险产品 | 不能。返回 412 + 图形验证码，反爬明确 |
| 金融监管总局产品备案 | 按批次通报，不逐产品公开 | 只能看通报稿 |

结论：真正的产品数据库拿不到结构化数据，产品这条线只能靠「人写的产品分析」。
